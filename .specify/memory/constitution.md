# Lucking 项目宪章

## 核心原则

### I. 规格驱动与可追溯

每项功能在实现前必须具有明确的规格，至少包含按价值排序且可独立验证的用户故事、
可测试的功能需求、边界情况和可度量的成功标准。计划中的设计决策和任务必须能追溯到
需求、用户故事或本宪章的强制约束；实现范围不得静默超出已批准的规格。需求或范围发生
变化时，必须先更新规格及相关设计文档，再调整任务与实现。

理由：稳定的需求来源和双向追溯能够减少范围漂移，并让评审者判断实现是否真正完成。

### II. 清晰边界与第三方数据源可替换性

系统必须保持前端、API、工作流、领域逻辑、数据基础设施和外部数据源之间的职责边界。
FastAPI/OpenAPI 是前后端接口契约的唯一事实来源；前端生成代码与手写代码必须分离。
事务型数据、分析型数据、临时状态和工作流编排必须分别由 MySQL、ClickHouse、Redis
和 Prefect 承担。任何跨边界使用或新增基础设施都必须在计划中说明数据所有权、生命周期、
一致性要求和更简单方案为何不足。不得在视图、路由或组件中堆积可复用的领域逻辑。

凡通过第三方 API 获取数据，领域和业务代码必须只依赖项目定义的供应商无关接口与规范化
数据模型，不得直接依赖第三方 SDK、端点、传输模型、错误码或供应商专有字段。第三方鉴权、
请求签名、限流、重试、分页、错误映射和数据转换必须封装在独立适配器中，并通过配置或
依赖注入选择具体实现。每个集成必须具备针对项目接口的契约测试，以及至少一个可替代实现
或测试替身，用于证明在不修改领域逻辑和公共 API 的前提下可以更换数据供应商。若供应商
能力无法映射到现有项目契约，必须先在规格和计划中显式修订契约及迁移影响，禁止将供应商
特例泄漏到业务层。

理由：显式边界可防止数据职责混乱和跨层耦合；供应商隔离可控制接口停服、价格调整、
协议变更和数据质量差异带来的迁移成本。

### III. 测试与质量门禁（不可妥协）

任何改变可观察行为、公共接口、数据模型或故障处理路径的变更，必须同时提供与风险相称
的自动化测试。缺陷修复必须先有能够复现问题的失败测试；新增接口或接口变更必须包含
契约或集成测试；关键用户流程必须具有精简的端到端验证。实现完成前，受影响范围的测试、
静态检查、类型检查和构建必须全部通过。若某项检查不适用，计划和评审记录必须给出具体
理由；不得以时间压力为由跳过质量门禁。

理由：可重复验证是持续演进和安全重构的前提，也是“完成”的客观证据。

### IV. 安全配置与最小暴露

秘密、令牌、真实密码和私钥不得进入版本控制、前端代码、日志或错误信息；仓库只保留
不含真实秘密的示例配置。所有外部输入必须在信任边界处验证，后端必须执行最终身份认证、
授权和数据访问控制。开发基础设施端口必须默认仅绑定回环地址；新增网络暴露、权限或
第三方集成必须在规格和计划中记录威胁、数据范围及缓解措施。破坏性数据操作必须有显式
警示，并优先提供可恢复路径。

理由：默认最小权限和最小暴露可降低配置失误、数据泄露及越权访问的风险。

### V. 可观测、可运维与保持简单

关键请求、后台任务、状态转换和外部依赖失败必须产生结构化、可关联且不含敏感信息的
日志或指标；错误必须保留足够上下文，并以可操作方式呈现。运行指引必须记录启动、健康
检查、验证、故障排查和安全停止步骤。第一版必须采用满足当前已验证需求的最简单方案；
引入新框架、服务、实时协议或抽象层前，必须证明现有技术栈无法合理满足需求，并在计划
的复杂度跟踪中记录依据。

理由：可诊断性缩短故障恢复时间，简洁性则控制系统的长期认知和运维成本。

### VI. MySQL 表结构一致性与可审计例外

项目拥有的新建 MySQL 业务表，以及发生结构性变更的既有 MySQL 业务表，在未获得特殊场景
例外时，必须使用 `id BIGINT NOT NULL AUTO_INCREMENT` 作为主键，并必须包含以下由数据库
维护的时间字段：

```sql
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
  ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间'
```

`id` 必须具有中文字段注释，例如 `COMMENT '主键ID'`。业务唯一性不得依赖自增主键替代；
具有业务唯一标识的表仍必须建立相应的 `UNIQUE` 约束。项目拥有的每张 MySQL 表必须具有
说明业务用途的中文表注释，每个字段也必须具有准确、非空的中文注释；该注释要求对获批
例外同样适用。ORM 模型、迁移脚本和实际 DDL 必须保持一致。

特殊场景仅限以下情况：纯关联表以复合外键表达唯一身份且没有独立生命周期；领域正确性、
分区或外部互操作明确要求自然键或复合键作为物理主键；或者表由外部框架完全管理且不承载
项目业务数据。任何例外必须在功能计划和 `data-model.md` 中逐表记录例外字段、业务理由、
被拒绝的默认方案、唯一性保障、创建/更新时间语义及迁移影响，并在宪章检查中获批。既有表
发生结构性变更时必须同步治理，不得以“历史表”为由静默延续不合规结构。

理由：统一的代理主键、数据库维护时间和中文元数据可降低跨功能建模差异，提高排障、
数据治理和迁移审查效率；受控例外保留了复合身份、分区及框架内部表的合理设计空间。

## 技术与文档约束

- 后端使用 Python 3.12、FastAPI、SQLAlchemy/Alembic，并以 OpenAPI 描述公共 API。
- 前端使用 Vue 3、TypeScript、Vite、PrimeVue 4、Pinia、TanStack Vue Query 和 Axios；
  图表统一使用 ECharts，具体约束以 `docs/frontend-technology-stack.md` 为准。
- 本地开发在 WSL2 中运行应用进程；Docker Compose 仅承载 MySQL、ClickHouse、Redis
  和 Prefect Server，具体操作以 `README.md` 为准。
- 应用代码必须提交依赖锁文件；依赖大版本升级必须通过受影响范围的完整质量门禁。
- 项目治理、规格、计划、任务、评审说明及面向项目成员的运行文档必须使用简体中文。
  代码标识符、命令、协议字段、第三方专有名词及外部标准要求的内容可以保留英文。
- 时间和跨系统时间字段必须使用 ISO 8601；服务端时间默认使用 UTC，展示层负责时区转换。

## 开发工作流与评审门禁

1. 使用 `/speckit-specify` 形成范围清晰、可验证且使用中文编写的功能规格。
2. 在 `/speckit-plan` 中记录技术上下文、边界、数据所有权、风险、质量策略和宪章检查；
   涉及第三方数据时还必须记录项目接口、规范化模型、适配器、供应商选择方式和迁移策略；
   涉及 MySQL 表时还必须逐表证明主键、时间字段和中文注释符合原则 VI，或记录获批例外；
   研究前及设计后各执行一次宪章检查。
3. 使用 `/speckit-tasks` 生成可追溯、依赖有序的任务；每个用户故事都必须包含先于实现的
   必要测试任务；第三方数据集成必须包含端口、适配器、契约测试和替代实现或测试替身任务，
   并包含安全、可观测性、文档和质量门禁任务。
4. 实现必须按任务依赖推进，完成项及时标记；不得在未更新规格和计划的情况下扩大范围。
5. 合并前评审必须确认需求追溯、架构边界、测试证据、安全影响、可观测性和文档均符合
   本宪章。任何例外必须在计划的复杂度跟踪中记录理由、替代方案和偿还条件。

## 治理

本宪章优先于仓库中的其他流程和惯例。任何修订必须提交书面变更，说明动机、影响范围、
迁移方案以及需要同步的模板和运行指引，并经过维护者评审批准。

版本遵循语义化版本：

- MAJOR：删除原则、重新定义不可兼容的治理规则或削弱既有强制约束。
- MINOR：新增原则或章节，或实质扩展现有治理要求。
- PATCH：不改变语义的澄清、措辞改进和勘误。

每个功能计划必须在研究前和设计后完成宪章检查；每次代码评审必须验证适用的强制规则。
无法合规时必须停止进入下一阶段，或在获得明确批准后记录限时例外及整改任务。维护者
至少在每次发布前复核宪章、模板和运行文档的一致性。
