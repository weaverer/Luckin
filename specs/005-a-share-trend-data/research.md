# 技术研究：A股行情数据交易日同步

## 决策 1：五数据类共享审计三表，业务表独立

**决策**：五张 ClickHouse 业务表（日线行情、复权因子、基本面指标、周K线、月K线）
各自独立；三张 MySQL 同步审计表（运行、尝试、质量问题）共享，
以 `data_kind` 字段区分 `DAILY_QUOTE` / `ADJ_FACTOR` / `DAILY_BASIC` /
`WEEKLY_KLINE` / `MONTHLY_KLINE` 五类数据。业务唯一键均为
`(trade_date, stock_id)`；周线与月线虽来自同一接口，但使用各自独立的数据模型
（用户明确要求），不共用表。

**理由**：五类数据字段集与消费语义不同、各自独立调度与恢复（NFR-009），
业务表必须分离；但五类数据共享完全相同的同步语义——权威运行、不可变尝试、
固定租约、幂等 run key与脱敏问题——金股验证过的审计模式一次实现、五类复用，
避免 5×4=20 张表的重复迁移、重复 ORM 和维护负担。`data_kind` 进入 `run_key`，
保证五类数据互不串扰。周月线拆表使两类周期数据可独立演进字段、
分区策略与清理范围（周线按月、月线可按年清理）。

**备选方案**：

- 五类数据各自四张审计表（20 张表）：迁移、ORM、Repository 和测试全面重复，
  与宪章 V 的简洁性冲突。
- 复用金股的 `broker_recommendation_sync_run`：金股运行身份是“目标月份”，
  本功能是“目标交易日”，语义不同；且金股已锁定其唯一键语义，跨功能复用会
  污染既有契约。
- 周月线共用一表以 `freq` 区分：用户明确要求独立模型；共用会迫使两类数据
  共享分区、字段和清理策略，演进互相牵制。

## 决策 2：四个独立 Provider 契约，而非聚合契约

**决策**：定义 `DailyQuoteProvider`、`AdjFactorProvider`、`DailyBasicProvider`、
`WeeklyMonthlyKlineProvider` 四个独立供应商无关契约，输入为目标交易日
（周/月线另加 `freq`），输出为规范记录、覆盖证据与 UTC 获取时间；
四个 Tushare Adapter 各自实现对应接口（周月线 Adapter 按 `freq` 分派到
两个独立规范模型）。

**理由**：五类数据来自四个不同端点、字段与错误语义不同，聚合契约会把五类数据的
生命周期和可替换性绑在一起：任何一类数据更换供应商都会牵动其他四类。
独立契约允许每类数据独立替换、独立契约测试、独立影子迁移，符合宪章 II
“供应商可替换性”逐项验证的要求；共享的覆盖证据结构与统一异常分类
仍然复用，避免重复设计。

**备选方案**：

- 单一 `MarketDataProvider` 聚合契约含四个方法：五类数据无法独立替换，
  任一来源变更都要求重审整个契约。
- Service 直接调用 Tushare Client：泄漏端点、字段和错误语义，违反宪章 II。

## 决策 3：按交易日提取全市场，不按股票循环

**决策**：`daily`、`adj_factor`、`daily_basic` 三个接口均以 `trade_date` 参数提取
全市场当日数据；`stk_week_month_adj` 以 `freq` 与周期最后交易日提取全市场周/月线。
任何数据类不得为获取单日全量数据按股票逐只循环调用。

**理由**：来源文档明确建议“循环日期提取全市场数据，不要循环 ts_code”；
按股票循环 A 股约 5,400 只会放大请求次数 5,400 倍并触碰每分钟 500 次限流，
同时增加停牌判断复杂度。按交易日提取时每交易日每类数据一次（或受控分页）请求，
回补 610 个交易日也只需约 2,400 次请求总量，在限流约束内。

**备选方案**：

- 按 `ts_code` 循环：请求量放大数千倍，限流下不可行。
- 混合（部分股票循环）：破坏完整性证明，无法断言“当日全市场已覆盖”。

## 决策 4：单次上限 6,000 行与全市场规模的完整性门禁

**决策**：单日全市场约 5,400 行，低于来源单次上限 6,000 行，单次请求即可容纳；
Adapter 仍必须实现提取完整性校验——请求完成、非空、行数未触顶、交易日一致，
任何一项不满足均不得标记成功。若未来全市场行数超过上限，Adapter 保留有界
循环提取能力（位置前进校验、重复检测、最大页数保护），启用前必须通过
部署账户或供应商沙箱验证续取参数有效。

**理由**：完整性门禁是“全市场已覆盖”的业务保证（FR-006/017、ED-003）：
即使当前单次请求可容纳，也不能假设未来市值扩容后仍如此；门禁使链路在
触顶时安全失败而非静默截断。验证过的循环能力作为已知上限突破后的演进路径。

**备选方案**：

- 假设单次请求必然完整：扩容或来源行为变化时静默截断，违反 ED-003。
- 无条件启用分页：来源未公开续取参数时猜测参数，违反 ED-008。

## 决策 5：复用交易日历判断交易日，非交易日成功跳过

**决策**：Flow 启动后查询项目交易日历（CN-S 上交所日历）判断目标时点是否为交易日；
非交易日不调用任何来源接口，直接记录“跳过”并成功结束；法定节假日自然跳过。
Cron 使用周一至五的固定时点（`0 9`、`0 17`、`45 17`、`30 18`，`Asia/Shanghai`），
周末不触发。

**理由**：规格 FR-001 要求交易日判断复用项目已有日历；已有 001 功能按
Tushare 日历每月同步 CN-S 日历，本功能只读取即可获得权威交易日判定。
周一至五 Cron 排除周末，法定节假日由日历判断跳过；Flow 内判断优于生成
动态 Cron，避免调度表达式随日历变化和回补场景的复杂化。

**备选方案**：

- 按日历生成未来一年的动态 Cron：调度表达式复杂、日历变更需重生成。
- 周末也触发再由日历判断：无谓调用 Prefect 与日历查询。

## 决策 6：调度时点与窗口

**决策**：复权因子 9:00（北京时间）启动、日线 17:00、基本面指标 17:45、
周/月线 18:30，均为每个交易日一次；计划时点来自 Prefect runtime，
目标交易日为计划时点所属交易日，失败重试不得顺延。

**理由**：四个时点由用户在与 /speckit-clarify 的对话中显式确认并写入规格
（FR-002 至 FR-005）：复权因子在开盘前完成入库（来源文档 9:15~9:20 完成，
9:00 启动留有重试余量）；日线、基本面与周/月线在收盘后依次执行，
周/月线依赖当日日线入库完成后同步，18:30 保证前者终态已形成。
`data_kind` 参数化 Flow 由四个 Deployment 复用，避免四份 Flow 代码重复。

**备选方案**：

- 单一 Flow 依次串行同步五类数据：任一接口失败阻塞后续接口，违反 NFR-009。
- 按来源文档窗口（15:00~16:00 等）调度：与用户确认的时点冲突，
  且不满足周/月线在日线之后的顺序依赖。

## 决策 7：回补策略（2024-01-01 起）

**决策**：上线初始化时四个接口均从 2024-01-01 起回补至当前增量，按交易日逐日展开、
逐日幂等（`backfill_batch_id + data_kind + target_trade_date` 确定运行身份）；
已成功日期跳过，失败或中断日期复用原运行新增尝试。约 610 个交易日 × 4 类
≈ 2,400 次来源请求，在“每分钟 500 次”限流下约 5~10 分钟内可完成，
实际按日串行执行并受整体截止时间保护。

**理由**：回补范围由用户显式确认（FR-020 与规格假设）；按交易日展开与
金股“按月展开”模式同构，复用同一套幂等恢复逻辑；限流估算表明 2024-01-01
起 2.5 年回补在单次回补流程内可行，无需特殊限流队列。

**备选方案**：

- 仅增量、不回补：历史分析场景无数据可用，不满足 FR-020。
- 回补全部历史（1991 年起）：数据量与时长超出首期需求，用户未要求。

## 决策 8：规范字段与单位

**决策**：日线行情规范字段为交易日、股票身份、未复权开/高/低/收、昨收、涨跌额、
涨跌幅、成交量、成交额；成交量与成交额采用来源单位并记录单位约定
（手、千元）到数据模型，消费方复权计算时按需换算。基本面指标规范化来源
19 个字段中项目需要的估值（PE/PE_TTM/PB/PS/PS_TTM）、换手率、量比、
总/流通市值、总/流通股本、除息指标与涨跌停状态；亏损公司 PE/PB 等
空值以 NULL 保存。周K线与月K线各自保存未复权开/高/低/收价及成交量、成交额、
涨跌额、涨跌幅、计算截至日期与周期最后交易日。

**理由**：规格 FR-008 限定规范字段范围，不保存来源附带的其他数据；
NULL 语义与“必需字段缺失”区分，亏损空值正常保存（用户故事 2 验收场景 2）；
部署账户实测（2026-08-02）`stk_week_month_adj` 仅返回未复权 12 字段
（无 qfq/hfq 复权价格），周/月线按实测只保存未复权价格；
复权对比由消费方结合日线复权因子自行计算。

**备选方案**：

- 只保存未复权价格（采纳）：来源实测不返回复权价格，消费方复权需结合日线
  复权因子自行计算。
- 保存来源全部字段：超出 FR-008 范围，扩大供应商耦合面。

## 决策 9：周/月线独立模型与周期归属

**决策**：周K线与月K线为两张独立 ClickHouse 业务表，各自业务唯一键均为
`(trade_date, stock_id)`，其中 `trade_date` 是来源返回的该周期最后交易日
（每周五或月末最后一个交易日）；周期类型由表本身表达，不再需要 `freq` 列；
周期归属判断只用于业务身份，不重新计算周期行情；来源输出含 `end_date`
（计算截至日期）时作为规范字段保存。

**理由**：用户明确要求周线与月线使用不同数据模型（同一接口、两个模型）；
来源以 `trade_date` 标识周期归属（用户提供文档明确“trade_date 对应每周五或
月末最后一个交易日”）；每日同步返回截至当日的周期数据时，同一周期内多日
请求返回同一 `trade_date`，排序键保证同键替换幂等；不重算周期行情避免与
来源口径产生偏差（规格假设）。

**备选方案**：

- 周月线共用一表以 `freq` 区分：与用户“数据模型不同”的明确要求冲突。
- 以同步触发日作为周期标识：同日触发但周期跨越时产生重复或错配。
- 自算周/月 OHLC：与来源口径不一致，且超出“只同步”范围。

## 决策 10：复用金股的运行治理模式

**决策**：运行治理完整复用金股验证过的模式——权威 run（唯一 run key、
`SUCCEEDED` 不可重开、失败重试复用原 run 新增 attempt）、认领时由数据库
UTC 时钟设置固定租约（大于 Provider 截止时间）、过期运行原子转 `ABANDONED`
后再重试、全批内存校验后单事务原子发布、失败回滚后独立事务写终态与
脱敏 issue、issue 只保存哈希与白名单摘要。

**理由**：这些模式已在金股功能中通过 MySQL 并发、事务回滚与幂等验收，
直接复用降低了本功能的设计与验证风险；“参考金股的工作流模式”的
用户要求也指向同一套治理语义。

**备选方案**：

- 简化审计（仅日志）：无法满足 FR-012/013 的权威结果与可追踪要求。
- 每数据类自定义治理逻辑：四套实现漂移，维护与验收成本上升。

## 决策 11：行情业务数据进 ClickHouse，审计留 MySQL

**决策**：五张行情业务表（日线、复权因子、基本面、周线、月线）保存到项目
ClickHouse；三张同步审计表（运行、尝试、问题）保存到 MySQL。
ClickHouse 表采用 `ReplacingMergeTree(updated_at)`，ORDER BY 业务键
`(trade_date, stock_id)`，按 `toYYYYMM(trade_date)` 分区。

**理由**：宪章 II 明确“分析型数据由 ClickHouse 承担”——行情数据是典型分析型
数据：回补后约千万行、按交易日批量追加、消费以按日期/股票的范围聚合查询为主，
列存压缩与按分区裁剪显著优于 MySQL 行存储。审计数据需要事务、唯一约束、
行级状态机与并发认领，是 MySQL 的既定职责（与金股一致），且审计表行数
远小于业务数据（每交易日每类 1 行），不会成为瓶颈。用户明确指定
“日线/周线/月线/复权因子都放 ClickHouse”，并经确认基本面指标同样进入
ClickHouse。

**备选方案**：

- 全部放 MySQL：千万级行量与按交易日追加的模式使行存储、索引和事务维护成本
  上升，且与宪章 II 的数据职责分配不符。
- 全部放 ClickHouse：审计状态机（唯一键、租约、原子认领）在 ClickHouse
  无行级事务与唯一约束，无法实现金股验证过的并发认领语义。

## 决策 12：ClickHouse 幂等与发布语义（单 block + 同键替换）

**决策**：发布流程为——全批候选内存校验后，以一次 ClickHouse 批量 INSERT
（单 block）写入对应业务表；INSERT 成功后在 MySQL 事务内写 attempt/run 成功
终态与全部计数。ClickHouse 侧幂等由 `ReplacingMergeTree` 的同键替换保证：
同一业务键（如同一交易日的同一股票）重复写入时以版本列（写入时间）取最新，
最终行集与成功执行等幂等价；单 block INSERT 在 ClickHouse 中原子提交，
查询任意时刻只能看到完整批次或上一状态，不存在半批可见。

**理由**：ClickHouse 不提供 MySQL 式事务回滚与 UPDATE/DELETE（初版行级
UPDATE 由 MergeTree 家族处理成本高），金股“失败批次对表零修改”的语义
需要转换为“失败批次对查询不可见 + 重试后行集收敛”：block 原子性保证
不可见半批，同键替换保证重试收敛。两写（CK + MySQL）之间无跨存储事务，
但收敛性由运行幂等（同一 run 重试不重复发布计数）与同键替换共同保证。

**备选方案**：

- 为审计与业务数据设计跨存储两阶段提交：引入协调器复杂度，违反宪章 V 简洁性。
- 业务数据也用 MySQL 写后复制到 CK：双写放大与一致性问题，无收益。
- 用 ClickHouse 实验性事务：依赖不稳定特性，不符合项目技术栈稳定性要求。
