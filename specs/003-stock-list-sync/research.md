# 技术研究：每日股票列表同步

## 决策 1：唯一外部端点与字段边界

**决策**：首期真实 Provider 只调用 Tushare `stock_basic`，固定请求字段：

```text
ts_code,symbol,name,exchange,curr_type,list_status,list_date,delist_date
```

不请求或保存其他 `stock_basic` 字段，也不调用任何其他 Tushare 接口。

**理由**：这 8 个字段完整覆盖规格要求的身份定位、代码、名称、交易场所、币种、上市状态
和上市/退市日期。请求完整默认字段后再丢弃仍会扩大数据访问范围，不符合最小暴露和
“只获取股票列表”的硬性边界。

**备选方案**：

- 调用行情、停复牌或公司接口补充信息：超出用户明确范围。
- 请求 `stock_basic` 所有字段：会获取地域、行业、实控人等非列表必要信息。
- 使用 Tushare SDK：引入无必要依赖，并增加供应商类型泄漏风险。

**来源**：<https://tushare.pro/document/2?doc_id=25>

## 决策 2：12 个分区与完整性证明

**决策**：对 `exchange ∈ {SSE,SZSE,BSE}` 与
`list_status ∈ {L,D,P,G}` 的笛卡尔积执行 12 次 `stock_basic` 调用。
所有分区成功、响应字段精确匹配、每分区少于 6,000 行且聚合非空时，Provider 才返回
`COMPLETE`。首期三个交易所是 `CN-S` 的固定完整范围，不提供排除任一交易所的配置。
单分区成功空集允许；恰好 6,000 行视为可能截断并失败。

**理由**：

- 官方默认状态是 `L`，不显式获取 `D/P/G` 会漏掉退市、暂停上市和未交易股票。
- 官方说明单次最多返回 6,000 行，但没有为该接口记录分页参数；按交易所和状态拆分可降低
  触顶风险，又不依赖未文档化能力。
- 12 次请求低于官方每分钟 50 次限制；正常一次同步不需要节流。
- 某个交易所/状态组合可能合法为空，不能让单个空分区导致永久失败；但整体空必须失败。
- 固定三个交易所使 Provider 覆盖证明和历史基线具有单一语义，避免配置缩小范围后被误判为完整。

**备选方案**：

- 一次只取默认 `L`：范围不完整。
- 每个状态全市场共 4 次：单分区更接近 6,000 行上限。
- 使用 `limit/offset`：官方输入未列出，不能把假设能力写入契约。
- 触及 6,000 行后仍发布：无法证明结果未截断。
- 将交易所集合开放为首期配置：会让“完整列表”的范围随运行变化，并与固定 12 分区验收冲突。

## 决策 3：专有字段到规范列表模型

**决策**：

- `L/D/P/G → ACTIVE/DELISTED/SUSPENDED/PENDING`
- `SSE/SZSE/BSE → XSHG/XSHE/XBSE`
- `symbol → security_code`
- `name → display_name`
- `curr_type=CNY → currency_code=CNY`
- `list_date/delist_date → listed_on/delisted_on`
- `ts_code → provider_security_id`，仅保存在 Provider 映射

Adapter 必须校验 `ts_code` 后缀与交易所一致，未知状态、交易所或币种立即失败。

**理由**：领域和数据库只使用项目规范枚举，未来 Provider 可在不改业务层的情况下提供等价值。
官方没有列出 `curr_type` 的完整枚举，因此首期只接受真实 fixture 验证的 `CNY`，
不能因目标为 A 股而盲目补值。

**备选方案**：

- 将 `ts_code`、`SSE` 或 `L` 直接写入核心股票字段：供应商耦合。
- 币种缺失时默认 `CNY`：伪造核心字段。
- 用名称推断交易所或身份：不可重复且风险高。

## 决策 4：通用 Tushare Client 的兼容扩展

**决策**：为 `TushareClient.call` 增加默认 `allow_empty=False` 的可选参数。
交易日历等现有调用保持空表失败；`stock_basic` 的单分区调用显式
`allow_empty=True`。股票列表 Adapter 在 12 分区聚合后再次执行非空门禁。

**理由**：当前 Client 会将任何成功空表映射为 `EMPTY_PAYLOAD`；但 `P` 或 `G`
等单分区可能合法为零。默认关闭可保持现有交易日历行为和测试不变。

**备选方案**：

- 全局允许空表：会削弱现有交易日历完整性。
- 在 Adapter 捕获 `EMPTY_PAYLOAD` 并猜测为空：混淆真实成功空表与 Client 错误。
- 修改响应 fixture 强行返回占位行：伪造数据。

## 决策 5：MySQL 当前值模型

**决策**：MySQL 使用四张表：

1. `stock_current`：项目 UUID、规范市场/venue/代码、名称、币种、状态、上市/退市日期及最近同步。
2. `stock_provider_mapping`：`provider_code + provider_security_id → stock_id`。
3. `stock_list_sync_run`：唯一计划周期、状态、尝试数、时间、分区证明、计数和安全失败摘要。
4. `stock_list_sync_issue`：同步或记录级质量问题的白名单上下文与哈希。

不保存完整列表快照、属性版本、行情或原始供应商行。

**理由**：股票列表是低量、需要唯一约束和原子 upsert 的当前业务参考数据，符合 MySQL
职责。规格明确不要求快照或属性全历史；四表已满足身份隔离、权威周期、问题诊断和当前查询。

**备选方案**：

- 只用 `stock_current` 并把同步状态写日志：不能用数据库唯一键保证计划周期幂等。
- 每日快照或 SCD2：超出当前值需求。
- ClickHouse：没有分析型时间序列，且不适合即时唯一与事务发布。
- Redis：MySQL 唯一键已能认领周期，无需第二状态源。

## 决策 6：稳定股票身份与 Provider 映射

**决策**：`stock_id` 为项目生成的不可变 UUID，语义是“交易场所内的上市身份”。
解析顺序：

1. 已有 `(provider_code, provider_security_id)` 映射优先。
2. 无映射时，若 `(venue_code, security_code)` 唯一命中现有股票，则绑定新 Provider 映射。
3. 两者均无命中时创建新 UUID。
4. 映射和规范键指向不同股票或存在多候选时，产生 `IDENTITY_CONFLICT` 并整批失败。

名称和状态变化更新同一身份；没有明确谱系的代码变化不得按名称猜测合并，新代码作为新身份，
旧身份因缺席而保留。

**理由**：`ts_code` 是供应商标识，不能作为公共业务键；venue + code 能辅助 Provider
迁移，但代码可能变化或重用，因此最终下游身份必须是项目 UUID。

**备选方案**：

- `ts_code` 主键：更换 Provider 会改变业务身份。
- venue + code 直接作为下游主键：代码变化会破坏引用。
- ISIN 或公司标识：`stock_basic` 不提供，调用其他接口又违反范围。

## 决策 7：全批校验与原子发布

**决策**：所有候选行先在内存规范化和校验，不写业务表。门禁包括：

- 12 个分区全部完成且未触顶；
- 总结果非空；
- 必填字段、币种、状态、交易所、代码后缀和日期关系合法；
- 完全相同的重复行去重并计数；
- 同一 Provider 标识或规范身份字段冲突则失败；
- 上一成功列表的任何 Provider 身份不得完全消失。

通过后，在一个 MySQL 事务中锁定唯一 `run_key`、批量 upsert 当前值与 Provider 映射，
并将同步结果设置为 `SUCCEEDED`。不删除缺席股票。事务失败整体回滚，再用独立事务写入
`FAILED` 与质量问题。

**理由**：规格只有成功/失败两种发布结果，不允许含未解决无效或冲突的列表成为最新权威值。
数据量不超过 10,000 条，内存候选集比 staging 表更简单。单事务保证消费者不会看到半批更新。

**备选方案**：

- 隔离坏行并发布其余行：与当前规格的完全成功门禁冲突。
- 逐行提交：会暴露半发布列表。
- 来源缺席即删除或改退市：违反 FR-010。
- staging 表：当前数据量和单进程校验不需要额外生命周期。

## 决策 8：计划周期、补跑和状态机

**决策**：`run_key` 由 `schedule_slug + scheduled_for_utc + scope_fingerprint`
规范生成并受唯一约束。状态机：

```text
PENDING → RUNNING → SUCCEEDED
                  ↘ FAILED → RUNNING
```

`SUCCEEDED` 不可重开；重复触发直接返回既有结果。人工补跑必须给出原计划时间并复用同一键；
`attempt_count` 递增，失败尝试细节由质量问题和 JSONL 日志保留。

**理由**：Prefect 的并发限制不能覆盖重复手工触发或重启，MySQL 唯一键是最终保障。
规格不要求保留每次尝试为独立业务实体，因此单周期单记录比批次层级更简单。

**备选方案**：

- 每次尝试新建一个权威 run：会产生不可区分结果。
- 仅依赖 Flow Run ID：不是业务计划周期。
- Redis 分布式锁：增加不必要状态源，且不能替代持久唯一约束。

## 决策 9：错误、重试和获取截止时间

**决策**：复用现有统一错误类别。Adapter 对当前失败分区处理网络、HTTP 429、明确短时频限和
5xx，最多额外重试 3 次，退避 30/120/300 秒；认证、权限、额度、配置、请求、载荷、
完整性、冲突和数据库错误不重试。整个 Provider 获取设 25 分钟单调时钟截止时间，
超时后即失败，给数据库终结和日志保留 5 分钟预算。Flow 不再叠加整批外部重试。

**理由**：只重试失败分区可避免前 11 个成功分区因第 12 个瞬时失败而反复调用；
截止时间保护 30 分钟成功标准。重试封装在 Adapter 符合宪章第三方边界要求。

**备选方案**：

- 每次失败重跑全部 12 分区：浪费额度并扩大失败面。
- Adapter 和 Flow 各自重试：最大次数相乘。
- 所有错误重试：确定性错误无法恢复。

## 决策 10：每日调度、日志与及时性

**决策**：新增 `stock-list-sync/default` Deployment：

- Cron：`0 9 * * *`
- 时区：`Asia/Shanghai`
- slug：`daily-stock-list`
- 并发：1，冲突策略 `ENQUEUE`

包括周末和休市日。业务日期从 Prefect 计划时间转换，不使用实际启动日。
将现有 JSONL 组件泛化为可配置文件名、字段白名单和及时性阈值；股票列表使用
`stock-list-sync.jsonl` 和 30 分钟阈值，交易日历继续使用原文件和 10 分钟阈值。

**理由**：符合规格和现有 Prefect 项目惯例；日志复用轮转、脱敏和统计逻辑，但避免两个领域
混用硬编码字段及目标。

**备选方案**：

- 仅交易日执行：规格要求每个自然日。
- 系统 cron：绕过项目编排和可观测性。
- 与交易日历共用 Deployment 或日志文件：调度、字段和时效目标不同。

## 决策 11：应用内查询与排除组件

**决策**：`StockListService` 提供按代码、venue、名称和状态筛选当前列表的应用内只读方法。
调用方必须在进入 Service 前完成认证、授权和访问控制；本功能不新增授权机制、
FastAPI/OpenAPI、前端、ClickHouse、应用 Redis、消息队列或实时推送。
在 10,000 条当前记录的验收数据集中完成一次预热后，以连续 100 次代表性查询验证至少
95 次在 1 秒内返回。

**理由**：规格没有公共网络用户场景，授权属于既有或未来调用入口的责任；当前列表查询
规模不需要分析数据库或缓存。明确数据规模、预热、样本数和查询组合后，性能验收可重复。
Prefect、MySQL 同步结果和 JSONL 日志已经满足运维观察。保持单体包是最简单方案。

**备选方案**：

- 新增 REST API：需要认证、授权、审计及新攻击面，超出范围。
- ClickHouse 保存每日快照：规格明确不需要快照。
- Redis 锁或缓存：MySQL 唯一约束与当前数据规模已足够。

## 决策 12：测试层级

**决策**：

- 契约测试：Memory Provider 与 Tushare Adapter 共享规范；MockTransport 审计
  `api_name` 只能为 `stock_basic`、字段精确、12 分区及统一错误。
- 单元测试：映射、身份、日期、触顶、空聚合、重复、冲突、身份消失、run_key 与状态机。
- 集成测试：MySQL 唯一键、批量 upsert、失败回滚、无删除、同周期并发和迁移。
- Flow/端到端：Mock Tushare → Adapter → Service → MySQL → 日志，验证重试、调度和安全。
- 容量测试：10,000 条候选记录完成规范化和发布，并审计零额外 endpoint。
- 查询性能测试：10,000 条当前记录、一次预热、连续 100 次代表性筛选，至少 95 次在 1 秒内返回。
- 统计验收：最近 30 次计划运行的及时率、连续 30 次重复/补跑和 5 分钟排障演练。

门禁为 `uv run ruff check .`、`uv run mypy src`、`uv run pytest`、
`uv run pytest -m mysql` 和 `uv run alembic upgrade head`。

**理由**：覆盖第三方替换、原子发布、唯一周期和严格范围这些最高风险点，并延续现有项目工具。

**备选方案**：

- CI 调真实 Tushare：依赖秘密、额度和网络，不稳定。
- 只做单元测试：不能证明 MySQL 事务和唯一约束。

## 研究结论

所有计划所需技术未知项均已解决，没有遗留待澄清项：

- 唯一端点：Tushare `stock_basic`。
- 完整性策略：12 分区、单分区 `< 6000`、聚合非空、历史身份不消失。
- 范围：固定 `CN-S` 的三个交易所，不提供交易所排除配置。
- 字段：固定 8 个必要字段。
- 当前值：MySQL 四表，单事务发布。
- 身份：项目 UUID + Provider 映射。
- 调度：北京时间每日 09:00。
- 组件排除：无 ClickHouse、业务 Redis、FastAPI、前端或新依赖。
- 查询：内部已授权调用，10,000 条数据上预热后 100 次查询至少 95 次在 1 秒内返回。

上述决策通过研究前宪章门禁。
